## Contradicts or bugs

Ours (gaps found by reading the friend's facts against ext/):
- `PlanCheck.Check` ignores natural solids for support (idea 1). Pieces resting on rocks or trees will be reported `unsupported`, which is wrong in game. Confidence high on the game rule (my own memory of WearNTear agrees), medium that every tree and rock collider counts.
- `Neighbours.Fires` says `burning` when fuel > 0. The game's IsBurning is also false when blocked above, wet, or submerged, and fuel stops dropping then. Confidence high.
- `bed_check` calls a bed sleepable with roof and cover only; the game also needs a Heat area at the bed and no Wet status. Confidence high.
- `PlanChecks.Overlaps` makes a noClipping overlap an error from 0.05 m; the game allows 0.2 m. Confidence medium-high (his Decomp note, my memory of `TestGhostClipping(…, 0.2f)`).
- `PlanCheck.Geo` takes every non-trigger collider, including nav-only layers (pathblocker). Measured by him as a 0.28 m error on a floor brazier. Confidence high.
- Mesh colliders are replaced by their bounds box in our contact model; the game uses the real collider. Medium.

The friend's own files:
- Doc vs Facts.cs disagree: doc section 9 says Player.m_maxInteractDistance 5, Facts.cs reads 3.5 live; doc says Dvergr ward radius undocumented, Facts.cs has 32 live; doc says Rested base time 480 (asset) while Facts.RestedBaseSec is 300 from the code default. The doc is stale or the asset value is unverified: treat 300 vs 480 as [U].
- Doc says burning area is "bounds +0.25"; code comment and Rules say `Bounds.Expand(0.25)` = 0.125 per side. Use 0.125 per side (Unity's Expand adds to the size). Confidence high.
- Doc sections 5-8 and 11 carry many [W] numbers (raid radii, Dvergr ward behaviour, weather wind ranges) that the doc itself marks open; do not turn them into hard checks.
- `Mat.WeakRatio` in Facts.cs uses `H < 0.5 ? H : V` as the span loss; for marble (H = 0.5) it flips to the vertical rule, which is a judgement call, not a game fact.
- Not wrong but worth knowing: the doc's [C] tag means "corrected", so a reader taking [C] as "from code" will misjudge the doc.

## Design hint: how Facts.cs is organised

- One `internal static class Facts`, about 720 members and 237 KB. Most of the size is XML-doc prose with the incident that led to the value (live run id, date), not data. Groups are banner comments (`// ---- world`, `placing`, `doors`, `using things`, `structure (WearNTear)`, `fire`, `smoke`, `night, beds, shelter`, `farm`, `neighbours`, ...).
- Every member has exactly one provenance attribute: `[Decomp(member, "file:line")]` (read from the decompiled assembly), `[Live(path, date)]` (read from the running game), `[Measured(how, date)]` (measured in play), `[Unmeasured(note)]` (a working value; says what would measure it), `[Rule(source)]` (not a game fact: a design rule, with who and why). Example: `[Decomp("Player.UpdatePlacementGhost: notOnTiltingSurface && normal.y < 0.8f -> Invalid", "Player.cs:3923")] const double TiltNormalY = 0.8`.
- Tables are small structs inside the class (`Mat(max, min, vLoss, hLoss)` with a derived `WeakRatio`), string arrays for layer sets, readonly dictionaries for damage factors and item-to-biome.
- Per-prefab values (sizes, snaps, flags, station fields, burn areas, smoke spawners) are NOT in Facts. They live in a data file written only by a live refresh tool (schema `vh.geometry/1`); an unknown prefab is an error that names the refresh call. Geometry is never hand-written.
- Rules about the facts: nothing else may restate a number; an owners audit checks (by IL) that every constant is read and that rule ids are unique; fields that must be audited are `static readonly`, not `const`, because a const is inlined. Golden tests hold live records to the pure rules (ghost rest point, tier ranking).
- `RuleBook`: `Rule.Hard(id, source)` (game legality, safety: removes an option) vs `Rule.Soft(id, why)` (our heuristic, advice only), declared as static readonly fields, registered at class init, listed by a tool.
- `Verdict` (the shape of every rule answer): `Ok`, `Code` (the game's own status name, e.g. NoBuildZone, MoreSpace, ExtensionMissingStation), `Why` (lazy text with the numbers), `N` (a dictionary of the numbers), `Ref` (the other piece involved).

For ext/: add `ext/Facts.cs` (game-free, linked by tests) with the same attribute set, move `WaterLevel`, `PenetrationTolerance`, `TiltNormalY`, `ContactGrow`, `Material` table and the ward/location numbers into it, add `scripts/lint_facts.py` (one provenance attribute per constant, no duplicate numbers in other ext/ files), and give `PlanProblem` a `Code`, a numbers dictionary and `Hard/Soft`. Keep the prose to one line per fact. Optionally a `facts` tool listing name, value, tag and source so a model can ask how sure a number is.
