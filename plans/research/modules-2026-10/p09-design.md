# p09-design: design kernel, validator, audit, plan schema (ClaudeNJevHeim)

Tags: [HARD] = the world keeps enforcing it after a ZDO spawn (so our plan_apply cannot dodge it). [GHOST] = only the hammer's placement ghost enforces it; a ZDO spawn skips it, but a plan that breaks it cannot be rebuilt or repaired by hand. [TASTE] = the friend's design preference (his "R" rules with "user" quotes), not Valheim. Reimplement from the descriptions; his repo has no licence.

Context: his validator (Validator.All, R1-R16) works on a design document, a walk grid and a stand chooser. Most of it is generator-side. What transfers is the rule set, the game facts behind it, and the Hard/Soft split (docs/decide.md "Hard and soft rules": Hard removes an option, Soft only advises).

## Contradicts or bugs

Ours, found while comparing (not run; read from code):
- ext/PlanRules.cs FireClearance: a cauldron/cooking station standing on a hearth overlaps the fire's box (gap 0) and IsStation makes it "hard", so the standard hearth+cauldron setup likely reports a fire-clearance error. His code exempts riders (centre over the fire's footprint, bottom >= top - 0.25 m). About 75% sure.
- ext/PlanCheck.cs Geo(): classification by name. `piece_walltorch` has WearNTear and "wall" in its name so IsWall is true; `piece_brazierfloor01` contains "floor" so Occupies is false and fire clearance ignores it. His live finding was the same bug class (a brazier read as a floor). About 80% sure for walltorch (assumes it has WearNTear), 90% for the brazier.
- 1 m free all round a fire, 1.5 m walkway, 2 m use zone are his preferences. Vanilla Valheim has no such placement rule that I know of (80% sure); our fire-clearance should be taste/warning, not error. The only hard fire facts are blocked-above, wetness, smoke escape (idea 6) and the cooking fire area (idea 4).
- ext/Shared.cs Verify.Plan accepts yaw + 180 for every prefab, so a flipped woodwall/stone_wall_4x2 (faced pieces) passes. Medium-high.
- ext/Plans.cs Apply: `y` missing defaults to 0 (spawns far below sea level 30) while plan_check uses the ground height for a missing y; unknown keys are ignored.
- PlanRules.PieceGeo loads NotOnWood, NotOnFloor, GroundOnly but no check reads them (grep).

His code and docs:
- DValidator sconce check: `want = p.MountHeight ?? 2.2` is computed but the test compares against 2.2, so a custom mount height always warns. High confidence (code read).
- DValidator door symmetry: the hinge table holds only `darkwood_gate`, so every other double door is never checked (silent skip). High.
- Plan docs drift: docs say the actions are place/remove/clear_area/level/tidy and name no `tolerance`/`front` key, but PlanSchema.cs also allows action `landscape` and place keys `tolerance`, `front`. The `roof` row of the element table has a garbled `family:` cell. Low impact.
- SitePrep.Prepend rewrites the plan file with a plain File.WriteAllText (non-atomic), same defect class as in his tools earlier reported.
- Unconfirmed numbers I would verify in our own decompile before using: interact reach 3.5 m (I recall Player.m_maxInteractDistance = 5 in older versions), "Smoked 2 hp/s", the 4 s smoke-blocked timer, 100-smoke cap. His method: decompile 1.0.16 plus live runs (vhtest*), but I could not check either.
- Not a contradiction: his support boxes (collider + 0.3 total), material table and 100 degree average match our SupportModel. His support is a per-step placement order estimate; ours is the steady state after 80 rounds. For a finished build ours is the right one; his order logic is idea 9.
